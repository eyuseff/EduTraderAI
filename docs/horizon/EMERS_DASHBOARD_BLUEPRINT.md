# EMERS Dashboard Blueprint

## 1. Dashboard purpose

The dashboard should orient the user before action by showing portfolio condition, risk, unresolved broker state, data status, and whether any action is required.

## 2. Five-second objective

In five seconds the user should know: Is my portfolio operating normally? Is risk within policy? Is any action required? Are there unresolved orders or broker events? Is data current and complete? Are opportunities worth reviewing? Is the system operating safely?

## 3. Information hierarchy

Environment and system safety, broker status, portfolio/risk condition, required actions, opportunities, positions, market context, and recent evidence.

## 4. Morning briefing

Illustrative only: Good morning, Eduardo. Markets are stable. Three opportunities meet your criteria. Two existing positions require review. No immediate action is required.

Names, numbers, and messages are illustrative only.

## 5. Portfolio condition

Show portfolio status, health, open positions, exposure, and current unresolved issues.

## 6. Risk condition

Show capital at risk, risk budget remaining, concentration, and policy state before returns.

## 7. Action requirements

Separate required action from optional review. No action required should be a valid dashboard outcome.

## 8. Opportunities

Opportunities should be candidates for review, not pressure to trade.

## 9. Positions requiring review

Highlight positions requiring attention because of risk, broker state, stale data, or planned exit review.

## 10. Broker and order status

Unresolved broker events and open orders must be visible.

## 11. Data and system health

Show data freshness, application health, publisher/coordination limitations, and degraded state.

## 12. Economic and market context

Show important context as informational, not deterministic prediction.

## 13. Pending approvals

Pending approvals must show age, risk, instrument, and whether action would contact a broker.

## 14. Alerts

Alerts should be grouped by severity and resolution path.

## 15. Personalization

Personalization may adjust layout but must not hide critical safety state.

## 16. Desktop layout

Desktop can use top status, left navigation, central briefing, right risk/action panel, and lower evidence timeline.

## 17. Mobile summary

Mobile should present compact status, alerts, risk, approvals, and broker state without hiding detail.

## 18. Empty and degraded states

Empty states should explain next safe action. Degraded states should block consequential action when required state is unavailable.

## 19. Dashboard success measures

Success measures include user understanding, low unresolved-state age, clear risk comprehension, and no pressure-to-trade behavior.

## 20. Open design decisions

Open decisions include layout density, chart placement, mobile summary depth, and alert prioritization.
