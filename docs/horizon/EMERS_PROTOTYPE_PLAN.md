# EMERS Prototype Plan

## 1. Purpose

Plan prototypes before implementation.

## 2. Prototype goals

Validate clarity, risk-first hierarchy, broker state, approval language, failure states, accessibility, and feasibility.

## 3. Prototype scope

Use simulated data only. No real broker credentials or customer data may appear.

## 4. Fidelity stages

Stage 1: Low-fidelity information architecture and screen layout. Stage 2: Medium-fidelity dashboard and opportunity-review flow. Stage 3: High-fidelity Paper trade-plan, approval, submission, and broker-status experience. Stage 4: Responsive mobile monitoring and alert concepts. Stage 5: Validated clickable prototype prepared for engineering handoff.

## 5. Priority screens

Home dashboard, Opportunity detail, Trade-plan builder, Risk review, Paper approval, Broker status, Orders, Position detail, and failure/unresolved order state.

## 6. Priority flows

Morning review, opportunity review, trade plan, risk review, approval, submission, broker acknowledgment, cancellation, unresolved state, and evidence review.

## 7. Prototype data

Simulated portfolio, opportunities, orders, broker states, alerts, and evidence only.

## 8. Interaction requirements

Prototype should include status changes, blocked actions, confirmations, and degraded states.

## 9. Safety-state requirements

Show Paper mode, broker state, stale data, rejected plan, unresolved order, and emergency stop.

## 10. User-review plan

Review with representative users only after scope and privacy safeguards are approved.

## 11. Accessibility review

Check keyboard, contrast, text size, labels, and motion assumptions.

## 12. Engineering feasibility review

Engineering should review contracts, state transitions, data needs, and implementation risk before build.

## 13. Security review

Security should review credential, session, approval, support artifact, and mobile risks.

## 14. Success criteria

Users can explain risk, status, required action, broker state, and evidence path without being pressured to trade.

## 15. Prototype risks

Risks include visual polish implying readiness, fake data appearing real, hidden risk, and premature framework selection.

## 16. Tools and format

Prototype tooling is undecided. No frontend framework is selected.

## 17. Handoff requirements

Handoff requires screen states, components, flows, copy, accessibility notes, and data contracts.

## 18. Approval gates

Implementation requires separate approval, technical design, tests, and release plan.

## 19. Deferred work

Live trading, production mobile approval, cloud deployment, and EMERS Score implementation are deferred.

## 20. Recommended first prototype

First prototype should cover Home dashboard, Opportunity detail, Trade-plan builder, Risk review, Paper approval, Broker status, Orders, Position detail, and failure or unresolved order state.
